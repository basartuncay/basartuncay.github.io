StillSolved

Launching · domain pending

Keeps Apple Support Community answers findable after the forum closes. Python 3.11 standard library, SQLite FTS5, Caddy, systemd, Chrome extension.

Problem
Apple’s Support Community is scheduled to close on 20 November 2026. Years of solved answers that people link to would stop working.
What I built
An indexer that reads the Internet Archive’s copies of the threads (never Apple’s live site), stores the question and accepted answer, and serves one page per thread with full-text search. A browser extension opens the saved thread when an Apple link fails. Pages show a 900-character excerpt and link to the archived original.
How I checked it
164,695 threads indexed, 63% with an accepted answer, about 36,000 in the last 24 hours (stats command, 19 Nov). 529 tests. A cache check went from 324 ms to 0.6 ms with one index hint and a regression test; a load test went from about 290 to 1,550 requests per second, p99 from 1.2 s to 16 ms. Deploy and rollback rehearsed in an Ubuntu container.
What I learned
Measure the thing you think you measured. One A/B test blamed my change for slower responses, but the script had killed a subshell, not the server. The real 1.2 s tail came from the Python server’s default listen backlog of 5.

Not public yet: the domain and server are still being set up, and a legal notice (Impressum) is required in Germany. Demo on request.

Service shutdown registry and repo scanner

Launching soon

A registry of announced service shutdowns, plus an offline scanner that flags hard-coded deprecated AI model IDs and other dependencies in a repo. Python, Node, GitHub Actions.

Problem
Services and AI models are retired on dates the vendor sets, and the notice often reaches only the account owner. Lists of shutdowns exist, but none told me whether my own repo was affected.
What I built
One TOML file per service, checked by a stdlib Python schema and built into a static site with RSS, calendar and JSON feeds. A zero-dependency Node CLI and GitHub Action reads manifests and source files for package names, hostnames, environment variable names and model IDs. A model ID only matches as a complete quoted string, so gpt-5 never matches gpt-5.1.
How I checked it
216 entries, 214 with a primary source (the vendor’s own page: URL, a short quote, the date read; the other 2 are marked secondary); 39 carry model-ID signatures. 91 Python tests and 44 Node tests, including one that fails if the scanner imports a network module. Scanner precision was measured on 111 public repos; see the QA notes. A census on 20 Nov found more than 2,200 non-fork public repos that contain at least one of 62 values retiring within 60 days (a lower bound that leaves out tests, docs and model catalogs; these are references, not proof that anything will break).
What I learned
Search snippets and vendor pages sometimes disagree on dates, so the vendor page wins and the correction is logged. I also searched for prior work before building the scanner and narrowed its scope to what I could not find.

Not public yet: name and launch date are still open.

certcadence: will your TLS renewals survive the shorter certificate caps?

Launching soon

A Python standard-library CLI and GitHub Action that reads Certificate Transparency history. crt.sh with Cert Spotter as fallback.

Problem
Public TLS certificates are capped at 200 days since March 2026, 100 days from March 2027 and 47 from March 2029, and Let’s Encrypt shortens its default to 64 days in February 2027. Domains renewed by hand, or by a fixed timer, will break on one of those dates.
What I built
The tool groups each domain’s certificates into renewal events, guesses whether renewal is manual or ACME-like from the rhythm, and prints the first cap that breaks it, with the rule used. Where the data is thin or truncated it answers UNKNOWN instead of guessing.
How I checked it
69 offline tests pass, including a hardened certificate-serial parser and real truncated crt.sh answers. Two snapshot studies on 20 Nov 2026: of the 80 largest German universities, 14 are ready, 63 at risk and 3 unknown; of the DAX 40 main domains, 14 ready, 25 at risk and 1 unknown. Every domain judged manual was at risk.
What I learned
CT logs show issuance, not deployment. Parallel certificate lines looked like 7-day renewals until I clustered them into events, and a review caught that one university’s sub-sites were being merged into its main domain. The tool now says what it inferred and why.

Studies are internal snapshots, not published. Not yet run as an Action on a real GitHub runner.

kvport: move Deno KV apps to Cloudflare

Alpha · not published

A Deno.Kv-compatible library on a SQLite Durable Object, plus a Deno CLI to export, import and verify data. TypeScript, Deno, Cloudflare Workers.

Problem
Deno Deploy is scheduled to shut down about six months after 9 October 2026, and apps that use Deno KV need a new home. Workers KV is eventually consistent, so code that relies on kv.atomic().check() cannot move to it as is.
What I built
The same API (get, list, atomic check, set, sum, min, max, versionstamps, expiry) on a strongly consistent Durable Object, so most code changes one line. A CLI scans code for unsupported features (queues, watch, cron), exports KV to a file, imports it into the Worker and verifies the copy.
How I checked it
129 conformance cases pass on both targets: real Deno KV as the oracle, and kvport inside Cloudflare’s local runtime. 225 Deno tests and 144 runtime tests pass. An end-to-end run moved 5,000 entries and the SHA-256 digests matched; a copy with one corrupted line was rejected. The key order of 500 random keys matches Deno’s. A security review and a code review found issues that I fixed with tests.
What I learned
Let the real thing be the specification. Where Deno’s behaviour (key order, limits, error types) disagreed with my assumptions, the case was rewritten to match Deno. The code review also caught an oversized expiry that was written before it was rejected.

Not tested on a real Cloudflare account or against a real Deploy database, only locally. No queues, watch or cron; TTLs and versionstamps are not preserved on import. Not published, package name undecided.

Also built

Four more, in short: problem, what I built, how I checked it, what I learned.

CRA role wizard Launching soon · legal review pending

Problem: the EU Cyber Resilience Act applies in stages, and the free tools I found tell you whether a product is in scope, not which role you have or from when. Built: a bilingual static page with yes/no questions, working without JavaScript, where every reason links to the article on EUR-Lex. Checked: 38 tests, including a hand-written decision table for every path, and an independent audit of the wording against EUR-Lex. Also added: a second module on product liability for software, under the new EU Directive 2024/2853 and the German Produkthaftungsgesetz that applies from 9 December 2026: questions lead to a likely role and a cited to-do list. Learned: the dates differ by role: reporting (Article 14) applies from 11 September 2026, open-source steward duties from 11 December 2027. I am not a lawyer: both modules are a reading aid, not legal advice, and nobody with legal training has reviewed them yet. The German text is mine and needs a native reader.

scamcheck Launching soon

Problem: students and newcomers get flat ads and messages that follow known scam patterns, and the warnings are spread over many official pages. Built: a static page in German, English and Turkish where you paste a text and see which patterns it contains; it runs in the browser, so the text is never sent anywhere, and each rule cites a consumer-protection or police source. Checked: precision 0.95 and recall 0.90, but only on 37 invented messages that I wrote myself, so real-world accuracy will be lower; nothing was measured on real messages. Learned: keyword rules miss new wording, so a clean result does not mean an offer is safe, and the page says so.

Bleibe Private · release pending

Problem: internationals in Germany juggle residence-permit deadlines, document lists and official letters in a language they are still learning. Built: an offline-first PWA in Turkish, English and German with holiday-aware deadlines, document checklists, a letter decoder, routine letter templates and a Karlsruhe first-30-days list; no account, no server, data stays in the browser. Checked: 78 unit tests plus Playwright runs on desktop and mobile in CI. Learned: templates that argue a legal position stay unshipped until a Migrationsberatung or lawyer has read them; the app is not legal advice.

A small company of sandboxed Claude agents Private · runs on my Mac

Problem: unattended automations, with no view of what they did or cost. Built: a Telegram inbox and a capped Claude Code agent that writes sourced notes under a five-rule constitution it cannot edit. Checked: a normal link run cost $0.09, a page with an injected instruction $0.07 (not followed, reported); caps of $0.50 and 15 minutes per run; 17 selftests in CI. Learned: permission rules alone did not contain the agent; an exact tool list and a pinned version did.
